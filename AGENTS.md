# AGENTS.md

Guidance for AI coding assistants working in this repository.

## What this is

A pipeline that migrates ITPA scalar tokamak databases (CSV, one row per
time-slice) into IMAS IDSs (mainly `summary`, plus a `temporary` IDS for
quantities with no IMAS path). Optionally, it also ingests each pulse into a
local SimDB (`--simdb`) or sends it to a SimDB server (`--remote NAME`). The pipeline is driven by **crosswalks**: reviewed spreadsheets that
map each source CSV column to an IDS path, a transform and a status.
`docs/migration.md` is the authoritative reference for the crosswalk format and
script behaviour. Read it before changing either.

## Commands

```bash
pip install -e '.[dev]'          # Python >= 3.11; installs the two console scripts below

# Migration: paths are relative to resources/input, resources/mappings, resources/results
idsmigration -e tc26 -d nfae39f2supp2.csv -m TC26_crosswalk.xlsx --validate   # validate only, write nothing
idsmigration -e tc26 -d nfae39f2supp2.csv -m TC26_crosswalk.xlsx [--simdb] [--per-time-slice] [-v] [--dd-version 4.1.1]
idsmigration -e tc26 -d nfae39f2supp2.csv -m TC26_crosswalk.xlsx --remote itpa [--replace] [--uploaded-by NAME]

# Blank crosswalk, or regenerate one for a new DD version keeping the manual columns
generate-crosswalk [--dd-version 4.1.1] [--output out.xlsx] [--num-rows 200] [--from existing.xlsx]

# Markdown profile of a raw CSV (NA markers, sentinels, per-machine stats) -> resources/profiles/
python -m itpa_imas_migration.dataset_statistics -d <file>.csv [--machine-col TOK]

black -l 120 src notebooks       # formatter (also run by pre-commit)
```

There is no test suite yet: pytest is declared in the `dev` extra, but no tests
exist. `idsmigration --validate` against a real dataset is the practical check
that a crosswalk or code change still loads, resolves against the DD and
type-checks. Some `docs/migration.md` command examples still use old
`idstools/scripts/...` paths from the IDStools fork; use the console scripts
above instead.

## Data and file layout

- `resources/input/` (source CSVs) and `resources/results/` (HDF5 output) are
  gitignored. The data can't be redistributed, so never commit it.
  `resources/data/` is also untracked.
- `resources/mappings/<name>.xlsx` is the canonical crosswalk. It has two
  sheets: `crosswalk`, and `DD`, a DD table dump that the `imas_unit`,
  `imas_dtype`, `imas_description` and `kind` formula columns look up.
  `resources/mappings/<name>.yaml` is its **sidecar**, found automatically from
  the mapping stem, with `sentinels`, `errors`, `resolve`, `standard_names` and
  `database` sections.
- `resources/mappings/csv/*.csv` are generated by a pre-commit hook
  (`xlsx2csv`) whenever an `.xlsx` is committed, so diffs are reviewable. Don't
  edit them by hand; edit the `.xlsx`.
- `docs/migration_data_logbook.md` records known source-data defects per
  dataset (typos, duplicate rows, unit mismatches). Update it when you find a
  new one.
- `notebooks/` analyse migrated data from a SimDB server (`SIMDB_REMOTE` in each
  setup cell) through its REST API. `notebooks/_simdb_common.py` is their shared
  helper. It downloads and caches the HDF5 files of multi-slice pulses in
  `~/.cache/itpa_simdb/`.
- All three scripts find the repo root by walking up to `resources/` or
  `pyproject.toml`. That is why they need the editable install.

## `idsmigration.py` architecture

`main()` runs these steps in order:

1. `load_sidecar` → `load_crosswalk`: reads the `crosswalk` sheet, strips
   strings and parses the dict and tuple literal cells.
2. `resolve_value_leaves`: for each `imas_path`, asks the DD (via the
   `imas.IDSFactory` at `--dd-version`) whether the node is a bare leaf or a
   structure. A structure gets a sibling pair, `value`/`source` by default or
   the pair given in `source_fields`.
3. `validate`: fatal problems raise and recoverable ones warn. See the table in
   the docs.
4. `build_write_spec`: precomputes each row's target branch and transform.
   `manifest` rows are routed to `temporary/<csv_dtype>` slots, with stable
   indices assigned in crosswalk row order.
5. `run_migration` → `process_pulse`: groups rows by `(machine, pulse)`, sorts
   them by time and builds one in-memory IDS set per pulse.

How values are written:

- `dynamic` leaves append one value per slice.
- `constant` and `static` leaves are written once. A later slice that
  disagrees is resolved with the sidecar `resolve` strategy (default
  `keep_first`) and counted in the end-of-run conflict summary.
- `resolve_writes` expands `&`-separated multi-path targets and
  dictionary-of-lists values into `(:)` AoS indices.
- Sentinels and dtype-mismatched values leave the leaf at IMAS empty.
- Per-machine `errors` write to the `_error_upper` siblings.

Output and SimDB:

- Without `--simdb`, every pulse is written with `write_pulse_dir` to
  `resources/results/<experiment>/<machine>_<pulse>/` (HDF5 backend).
- With `--simdb`, one entry is ingested per pulse, with no input files. SimDB
  keeps a numeric array only as `{min, max}`, so:
  - a single-slice pulse is metadata only. `summary_metadata` runs SimDB's
    `load_imas_metadata` on the in-memory `summary` IDS.
  - a multi-slice pulse is also written to HDF5 and attached as the entry's
    output, and SimDB reads the `summary` metadata from those files.
- In both cases `extract_variables` and `make_manifest` turn the `temporary`
  IDS into manifest metadata: a variable with a sidecar `standard_names` entry
  goes under `standard_name.*`, any other under `unmapped.*`.
- `--remote` swaps the local DB for `upload_to_simdb_server.SimDBServerUploader`,
  passed as `db` (same `insert_simulation`/`delete_simulation` interface).
  `main(argv, db=...)` accepts any such object, which is handy for testing
  without a real SimDB.
- `new_ids` stamps run-wide metadata (`IdsHeader`) on every IDS:
  `creation_date` = migration time, provenance references = labelled URLs
  from the sidecar `database` section (`<url> (paper)`, ...), and `code/*` read from git (`code_info`).
  Crosswalk rows may not target `ids_properties/creation_date` or `code/...`.

Machine-keyed features (dict `source`, `errors`, `--simdb`) need a crosswalk row
that maps to `summary/machine`. Per-pulse grouping also needs one that maps to
`summary/pulse`.

## Conventions

- When you change script behaviour, update `docs/migration.md` in the same
  change. The docs describe exact semantics (gating, validation outcomes,
  sentinel type matching) that users depend on.
- Sentinel matching checks both value and type. In YAML 1.1, an exponent float
  needs a decimal point and a signed exponent (`1.0e+38`). Otherwise it is
  parsed as a string and never matches a numeric cell.
- When you author crosswalk rows, use the `imas-dd` MCP server to look up DD
  paths. Status meanings are `mapped`, `mapped_caveat`, `manifest`, `derived`
  (not implemented, skipped) and `discard`. Record the reasoning in `notes`.
